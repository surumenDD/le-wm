## 3. 各軸の解釈

### 3.1 軸 A（Eval パラメータ）の解釈

#### 事実
- (2) と (3) は完全一致で `50/25/30`。論文 (1) は `150/100/10`。
- (4) HF config.json は **構造上 eval パラメータを持たない**。
- hydra は CLI から既定値を任意に上書き可能（`python eval.py eval.eval_budget=150 ...`）。
- 公開リポジトリ内に、図 3 の数値を生成した際の **CLI コマンドを示すシェルスクリプト / Makefile / READMEのコマンド例は存在しない**（grep で確認: `stable-worldmodel/scripts/minerl.sh` のみ存在し、Two-Room 用ではない）。

#### 現在検討中の点
- (1) 論文値 `150/100/10` と (2)(3) yaml 既定 `50/25/30` のどちらで図 3 の 87% が生成されたかは、リポ側資料からは判定不能。
- 著者照会で確定する予定（質問本文は `著者DM草案.md` 参照）。

#### 採用方針
- 第一試行: 論文 Appendix 値 `eval_budget=150, goal_offset_steps=100, solver.n_steps=10` を採用する。CLI override または yaml 修正で実現。
- 第二試行: 保留（第一試行で 87% に乗らない場合に `50/25/30` での再試行を検討）。

### 3.2 軸 B（モデルアーキテクチャ）の解釈

#### 論文側の事実
- 論文 (`appendix.tex:311`):
  > The history length is set to **3 for the PushT and OGBench-Cube environments, and to 1 for TwoRoom**.
  - **per-env** で明示。Two-Room を特筆して `1` と書いている。
- 論文 method (`3-method.tex:35,49`): 一般形 N で書かれ、$\mathbb{Z} \in \mathbb{R}^{N \times B \times d}$ と定義。env ごとに $N$ が異なる定式化。

#### 3層チェーン（訓練 yaml → コンストラクタ引数 → 重み形状）

論文の "history length" と HF config.json の `num_frames` は、コード上で **同一の値**を経由する3層チェーンで直結している。

```
[Layer 1: 訓練 yaml]          [Layer 2: コンストラクタ引数]          [Layer 3: 重みの形状]
wm.history_size = N  ───→  Predictor(num_frames=N, ...)  ───→  pos_embedding: (1, N, input_dim)
```

| Layer | 役割 | le-wm リポ（出典） | stable-worldmodel リポ（出典） |
|---|---|---|---|
| 1 | 訓練 yaml の値 | `config/train/lewm.yaml:47` → `history_size: 3` | `scripts/train/config/lewm.yaml:43` → `history_size: 3` |
| 2 | `num_frames` 引数として渡す | `train.py:95` → `num_frames=cfg.wm.history_size,` | `scripts/train/lewm.py:160` → `num_frames=cfg.wm.history_size,` |
| 3 | `pos_embedding` を確保 | `module.py:262` → `nn.Parameter(torch.randn(1, num_frames, input_dim))` | `stable_worldmodel/wm/lewm/module.py:269-271` → 同等 |

- 全 Layer が `num_frames` という同一値を経由する。
- 訓練 data yaml (`stable-worldmodel/scripts/train/config/data/tworoom.yaml`, `le-wm/config/train/data/tworoom.yaml`): いずれも `wm.history_size` の **env 別 override は無し**（grep 確認済）。
- ⇒ Two-Room 専用で `history_size=1` を渡すには、CLI 上書き（例: `train.py wm.history_size=1`）以外の経路はリポ側に存在しない。

#### HF 公開モデル側の事実（観測値）

- HF `config.json`（取得元: <https://huggingface.co/quentinll/lewm-tworooms/raw/main/config.json>）:
  - `predictor.num_frames: 3`
- HF `weights.pt`（取得元: <https://huggingface.co/quentinll/lewm-tworooms/resolve/main/weights.pt>, ファイルサイズ 72,290,849 byte）を本ブランチ作業環境で `torch.load(..., weights_only=True)` で開き、state_dict を直接走査（実施日: 2026-05-14、ホスト: コーディング環境）:
  - `predictor.pos_embedding`: shape `(1, 3, 192)` dtype `torch.float32`
  - 総パラメータ数: 18,042,672
  - 総 state_dict キー数: 303
- 上記 3層チェーンを Layer 3 から逆算: `pos_embedding` 第2次元 `3` → Layer 2 で渡された `num_frames=3` → Layer 1 で `wm.history_size=3`。
- ⇒ **HF 公開モデルが `wm.history_size=3` で訓練された** ことが、yaml / コンストラクタ呼び出し / 重み形状 の3層すべてで整合的に確認可能。

#### 現在検討中の点
- 論文記述 "history length = 1 for Two-Room" と、HF 公開モデルの `num_frames=3`（重み `pos_embedding: (1,3,192)` と整合）の食い違いがなぜ生じたかは未解明。
- リポ内に Two-Room 専用で `wm.history_size=1` を渡す経路（shell script / Makefile / README コマンド例）は存在しない（grep 確認済）。
- 著者照会で確定する予定（質問本文は `著者DM草案.md` 参照）。

#### 採用方針
- HF checkpoint を使う前提で `num_frames=3` 固定で planning 評価する（`num_frames` を変更すると state_dict load で `pos_embedding` の shape mismatch が発生し、ロード不能）。
- 論文の `history=1` 仕様での再現は再訓練が必要なため、本スコープ（HF checkpoint で 87% を再現）外とする。
- 軸 A と軸 B は独立。軸 A は yaml/CLI 上書きで対応可能、軸 B は HF checkpoint 利用前提では変更不可。

## 4. Hydra による override の可能性

yaml 既定値が実際の実験で使われた証拠の有無を整理する:

### 4.1 override 機構の存在
- stable-worldmodel/le-wm は **hydra ベース**（`@hydra.main` デコレータ、`eval_wm.py:54`, `eval.py:49`）。
- hydra は CLI 引数で yaml の任意キーを上書き可能（例: `python eval_wm.py eval.eval_budget=150 eval.goal_offset_steps=100 solver.n_steps=10`）。
- したがって yaml 既定値はあくまで「指定がない場合のデフォルト」で、**実際の実験で何が使われたかは yaml だけからは分からない**。

### 4.2 公開リポ内に「実際の実験コマンド」が記録されているか
- `find scripts/ -name "*.sh"` の結果: stable-worldmodel/scripts/minerl.sh のみ（Two-Room 用ではない）。
- `Makefile`: 存在せず。
- READMEs: `policy=pusht/lewm` 形式の一般例のみで env 別 CLI override 例は無し。
- ⇒ **「yaml 既定値で実験した」と「CLI override した」のどちらも、リポ側に証拠が無い**。

### 4.3 結論
- yaml 既定 `50/25/30` が実際の実験で使われたという証拠は無い。
- 論文値 `150/100/10` が CLI override で使われたという証拠も無い。
- ⇒ 図 3 の値を生成した eval 設定は、リポ側資料からは確定不能。
